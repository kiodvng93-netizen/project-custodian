## 2. Risk of losing files: highest priority

1. **Uncommitted work.** `sprites.js`, `assets/tiles/`, and the edits to `main.js`, `player.js` and `index.html` exist only on this disk.
   Fix: commit and push now. From now on, commit after every working step ("robot sprite animates", "fix draft bug").
2. **`patcher.html` can silently damage code.**
   - **It edits files with no backup.** `REPLACE_FILE` overwrites whole files.
   - **Matching is fuzzy and ignores indentation.** It replaces the **first** block of lines that matches after trimming spaces, so if similar code appears twice it can edit the wrong place.
   - **It throws away indentation.** That explains the messy indentation scattered across the code.

   With Claude Code you no longer need it: edits are made directly and git can undo them. Delete it, or move it to an `archive/` folder.
3. **Saves live only in browser `localStorage`.**
   - "Clear browsing data" wipes progress.
   - Opening the game a different way (double-clicking the file vs. a local server) gives a different, empty save.

   There is no save version number, so adding a new perk later will give `NaN` stats on old saves (`js/player.js:49-55`). See §5.
4. **Art masters.** The 2–4 MB AI renders are your *source art*. Keep them backed up (they are in git, which is good), but the game should load small exported copies (see §6).
5. **Keep the GitHub repo private** unless you intend to publish it.

## 3. Context overflow: why AI sessions run out of room

| What eats context | Size | Fix |
|---|---|---|
| `PROJECT_STATE.md` pasted into a chat | ~150 KB (≈45k+ tokens), mostly **an outdated copy of the code** (it lists 11 files, but there are 14 now, and `config.js` differs) | Delete the code copy. Claude Code reads the real files itself |
| `weapons.js` | ~50 KB | Split into one file per weapon (~100–250 lines each) |
| `main.js` | ~34 KB | Split by job: `camera.js`, `input.js`, `hud.js`, `draft.js`, `workshop.js`, `game.js` (loop) |
| Unclear "where does X live?" | Each session re-reads everything | A short `CLAUDE.md` file map, so the AI opens only the 1–2 files it needs |

Recommended doc layout (replaces `PROJECT_STATE.md`):

```
CLAUDE.md            ~60 lines: what the game is, how to run it, file map, coding rules
docs/DESIGN.md       rules, mechanics, economy (Part 1 of PROJECT_STATE, kept up to date)
docs/ROADMAP.md      the 105-step plan (Part 2), with [x] done markers
docs/AUDIT-*.md      this file
```

`CLAUDE.md` is loaded into every Claude Code session automatically, so you never paste context again.

Working rules that keep sessions small:
- **One feature per session.** When it works, commit and start a fresh session.
- **Keep files under ~400 lines.** When one grows past that, ask for it to be split.
- **Ask for a plan first** on anything big ("plan how to add rooms"), then implement step by step.
- **Don't paste code into the chat.** Name the file or the feature instead.

## 5. Code health

**Good:**
- Central `config.js`.
- A spatial grid exists.
- Decals are baked to offscreen chunks.
- Delta-time loop with a clamp.
- Telemetry HUD.

**Problems:**
- **Config values exist but are ignored.** Hardcoded numbers are used instead for `SPATIAL_GRID`, `DECALS`, `GIBS`, most of `JUICE`, `CHESTS.interactionRadius` and others. Changing config "does nothing", which confuses AI and human alike.
- **Run state is stored by mutating `CONFIG`.** Upgrades rewrite the config itself. Config should be read-only, with run stats in a separate `runState` object that's rebuilt on restart.
- **Copy-pasted weapons.** Mortar, Incinerator and Storm Spore share ~70% identical code, as do Saw/Volt and Tesla/Volt. Shared base classes would roughly halve `weapons.js`.
- **Long safety chains** like `window.CONFIG && window.CONFIG.X && window.CONFIG.X.Y`. This is AI "defensive" noise. Config is always loaded first, so plain `CONFIG.X.Y` is fine.
- **Everything talks through `window.*` globals.** This is OK for now. When splitting files, keep the same script-tag approach; don't jump to a build tool yet.
- **Dead code**: `PickupManager.update`, `SpriteManager.isReady`, `slotCost`, `Telemetry.isRunning`.

**Performance (target: 60+ enemies at 60 FPS):**
- **Hit checks skip the spatial grid.** Projectiles, Storm Spore, Tesla chains and walls (~377 of them) check every enemy every frame. Route these through the grid.
- **Damage numbers spam.** Flamer, drone and ash-zone damage create one text per enemy **per frame**. Accumulate the damage and show it every ~0.2 s instead.
- **Pickups are never capped or merged.** Merge nearby XP gems the way Brotato does.
- **Per-frame garbage.** For example, `[...enemies, ...nests]` builds a new array every frame, and `Telemetry.recordEvent` runs on every kill.

## 6. Art and the 3/4 view

Today:
- **Only the robot and the 2 tiles use images.** Enemies, boss, nests, chests and walls are code-drawn shapes.
- **The PNGs are 1536×1024 with a white background.** Code fakes transparency by deleting near-white pixels (`js/sprites.js:81`). That eats into white highlights, and it fails when the game is opened by double-clicking `index.html` (`file://`).
- **The robot is drawn at 54 px from a 1536 px sheet**, about 30× more pixels than needed. Its frames are sliced inconsistently (`/8` vs `/7` columns), so frames bleed into each other.
- **No depth sorting.** 3/4 view needs "draw things lower on screen last" (y-sort) plus soft ground shadows, or enemies will appear to stand on top of walls and each other.

Recommended asset pipeline:
1. **Keep sources separate.** Put the big AI renders in `art_source/`; that's backup only.
2. **Clean them up** in Aseprite (paid), LibreSprite (free) or Photopea (free, web):
   - Remove the background so you have true transparency.
   - Resize to ~2× display size, e.g. 96–128 px for the robot.
   - Lay frames on an even grid.
3. **Export** to `assets/` as one sheet per character plus a small JSON listing the frames (Aseprite exports this). That takes ~30 MB down to well under 2 MB.
4. **Replace the 3-entry manifest in `sprites.js`.** It should read those JSON files and wait for every image before the game starts.
5. **Run through a local server** instead of double-clicking. The VS Code "Live Server" extension is one click. This also fixes the `file://` problems.

## 7. From arena to Metroidvania: what's missing

The world today is one open field, regenerated randomly each run, with the hub hardcoded at (0,0). There is no concept of a room, door, map file or enemy-vs-wall collision. A Metroidvania needs:

1. **Room data in files, not code.** Use a free level editor: **LDtk** (recommended, made for exactly this) or Tiled. You draw rooms visually and the game loads the JSON.
2. **A `Room`/`Scene` manager** that loads one room's tiles, walls, enemies and exits, and swaps rooms at doors.
3. **Tile-based collision** for both the player and enemies (replaces 377 loose wall rectangles).
4. **Ability gates**, the core of Metroidvania: dash over gaps, shields through corruption, and so on. These are flags in the save file.
5. **A versioned save** (`{version: 2, ...}` + a migration function) that stores unlocked abilities, visited rooms and opened gates.
6. **A world map screen** built from visited rooms.

Engine question: staying in plain JS is reasonable, since it's working and an AI writes it well. Don't rewrite now. Revisit only if rooms and tilemaps become painful. At that point **Phaser 3** (still JS, has LDtk/Tiled loaders, cameras and sprite sheets built in) is the gentlest step up.
